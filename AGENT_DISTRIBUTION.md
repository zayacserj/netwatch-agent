# Доставка и привязка агента NetWatch

## Пользовательский сценарий

1. В Telegram выполнить `/add_router` и получить единственную команду установки.
2. Выполнить весь блок команды от root на OpenWrt.
3. Блок скачивает конкретную версию `deploy_files/agent3_fixed.sh` из GitHub
   по SHA коммита, проверяет SHA256 и синтаксис, затем вызывает `pair`.
4. Агент проверяет зависимости, сохраняет резервные копии, привязывается к Pi,
   устанавливает два задания cron и делает первую отправку данных.

Код подключения действует 15 минут. Код не передаётся в URL GitHub.
Единственный адрес API задаётся через `PI_URL_PUBLIC`: публичное имя хоста с HTTPS.
В боте больше нет локальной команды, выбора сети или подстановки `PI_URL`.
Литералы IP, localhost, HTTP и отсутствие канонического адреса отклоняются до
создания кода. Адрес должен работать из интернета и из домашней сети.

В домашней сети тот же домен может разрешаться непосредственно в адрес Pi
через локальную DNS-запись, либо работать через NAT reflection. В обоих случаях
HTTPS-сертификат должен соответствовать одному и тому же домену. Запись AAAA
нужна только при работоспособном IPv6-маршруте к API. Эти настройки не меняются
установщиком. До подключения новых пользователей нужно отдельно проверить
публичный DNS, сертификат и проксирование Caddy из обеих сетей.
Секрет агента не печатается в терминал или журнал. Конфигурация имеет права 600,
каталог резервных копий установки — 700. Содержимое конфигурации и неуспешного
ответа `/pair` не нужно отправлять в чат.

Блок `/add_router` запускается от root. Он скачивает агент через `curl`
или штатный `uclient-fetch`. Если загрузчик нужно подготовить, блок
устанавливает `curl` и `ca-bundle` через `apk` или `opkg`.
После проверки SHA-256 агент с параметром `--install-deps` сам устанавливает
недостающие зависимости и проверяет наличие `crontab`, `logger` и других
стандартных утилит до обращения к API привязки. Нужны интернет, DNS,
верное время и место во флеш-памяти. Podkop необязателен: агент проверяет
его состояние, если он уже установлен.

## Повторная установка

Агент проверяет сохранённый секрет по запрошенному адресу через
`GET /agent/identity`. Если сервер подтверждает тот же `router_id`, обновление
сохраняет идентификатор и секрет; новый код не расходуется. Если домен API
изменился, но подтвердил ту же привязку, обновляется только `PI_URL` с
сохранением остальных настроек. Это позволяет перейти с прежнего локального
адреса на единый HTTPS-домен без повторной регистрации.
Запуск из уже установленного файла поддерживается: файл сначала копируется
в отдельный кандидат, а не поверх самого себя.

Для явной смены сервера или повторной привязки служит `pair --re-pair` со свежим
кодом. Команда из бота этот флаг автоматически не добавляет.
В ответе `/pair` используется идентификатор, подтверждённый сервером, в том числе
при нахождении существующего роутера того же пользователя по MAC.

Одновременные установки на одном роутере блокируются каталогом
`/tmp/netwatch-install.lock`. После штатного завершения/сигнала блокировка
снимается; после аварийного выключения она исчезает при перезагрузке.

## Расписание и журналы

Устанавливаются только собственные задания NetWatch:

- снимок устройств — каждую минуту;
- здоровье роутера и задержка выбранного прокси — каждые 5 минут.

Задания других программ сохраняются. Старые задания `run`/`snapshot` для
канонического агента и `/tmp/agent3.sh` заменяются двумя актуальными строками.
Повторный запуск не дублирует задания. Перед записью проверяется, что crontab
не изменился после подготовки кандидата.

Журналы направляются в системный лог: `logread -e netwatch-agent`.
USB-накопитель и каталог `/mnt/usb` не требуются. Сеть, DNS, Podkop и Wi-Fi
не перенастраиваются; старый `wifi-monitor` автоматически не запускается.

## Ошибки и восстановление

Резервные копии находятся в `/etc/netwatch/backups/install.*` (или `cron.*`
для отдельного обновления расписания). При отказе установки cron агент и
конфигурация восстанавливаются из локальных копий.

Код, регистрация роутера и секрет сохраняются одной транзакцией на Pi.
Просроченный/использованный код отклоняется. Конфликт идентификатора с роутером
другого пользователя не расходует код и не меняет чужой секрет.

После сетевого таймаута запроса `/pair` автоматического повтора нет: результат
на сервере может быть неизвестен. Сохранить каталог операции и использовать
свежий код после проверки. `pairing.pending_id` сохраняет идентификатор между
попытками. Серверное сопоставление по MAC ограничено владельцем роутера.

Неудачная первая отправка после успешной установки не удаляет рабочую
привязку: выводится сообщение, а cron повторяет отправку по расписанию.

## Публикация следующей версии

Сначала опубликовать и протестировать агент и совместимый API. Затем обновить
SHA коммита и SHA256 артефакта в генераторе команды бота. Команда не должна
ссылаться на движущуюся ветку `master`/`main`.

При доставке на Pi сначала обновить API/DB, затем бота. Уже работающие роутеры
не обновляются автоматически от изменения ветки GitHub. Рабочие файлы Pi,
секреты и SQLite не заменяются через `git pull`.
